# تصميم بوت الإدارة «برج المراقبة» — v1

القرار المعماري والتصور الكامل لتحويل قناة تيليجرام الإدارية (باتجاه واحد،
أُنشئت في OPS-1) إلى لوحة قيادة تفاعلية كاملة للمشغّل. هذه الوثيقة تسبق
الكود (§15.15) وتُحدَّث مع كل مرحلة.

## 0 — الحكم على الاقتراح الخارجي المُقيَّم

الاقتراح المستلم (HappyKube / TowerBot / قالب aiogram) جرى تقييمه ورُفض
كأساس، للأسباب الموثقة:

- يصف مشروعًا آخر: بوت تيليجرام للعملاء + SerpApi/OpenAI +
  `application_service.py` — كلها من المشروع الشخصي القديم (المرجع
  المقروء فقط)، لا من هذا المستودع. عملاء هذا المشروع على واتساب حصريًا.
- مراجعه غير قابلة للتحقق ولا تُبنى عليها قرارات معمارية.
- «معمارية نظيفة بأربع طبقات» تكرر ما يقدمه المستودع أصلًا (سلطات
  مختبرة + عملاء حقن + منفذون نحيفون + RLS).
- تبنّي مكتبة بوت كاملة لبوت مشغّل واحد = تبعية بلا حاجة؛ نمط المستودع
  المجرب: عميل HTTP بنقل قابل للحقن + حلقة systemd (نفس نمط واتساب).

المبادئ الصحيحة المأخوذة منه: تيليجرام واجهة تحكم فقط؛ معالج نحيف ←
سلطة ← عارض؛ لا استنساخ لأي ريبو؛ تطبيق تدريجي.

## 1 — القوانين الحاكمة

1. **قراءة أولًا**: الأفعال المؤثرة قليلة ومحروسة بموافقة مزدوجة.
2. **لا PII إطلاقًا** (§15.13): رموز TEN-#### فقط؛ كل مخرج يمر بفلتر
   الأسرار (دفاع مزدوج فوق عقد العارضين).
3. **لا مسار إرسال جديد**: الأفعال تستدعي السلطات المختبرة الموجودة
   (descend، run_daily_delivery، close، provisioning) — البوت لا يخترع
   منطقًا.

## 2 — المعمارية

```
Telegram getUpdates (long-poll)
        ↓
career/telegram/console.py   ← الموجّه: هوية → أمر/زر → سلطة → عرض
career/telegram/views.py     ← عارضون نقيون (بيانات ← نص عربي + أزرار)
        ↓
سلطات المستودع الموجودة + قراءات SQL owner-role
```

قرارات مقفلة:

- خدمة systemd منفصلة `career-admin-bot.service` — عزل كامل عن
  `career-worker.service` (مسار العملاء مقدس).
- long-poll لا webhook: صفر تعريض عام.
- صفر تبعيات جديدة.
- مؤشر getUpdates يُحفظ في جدول `admin_bot_state` (يدخل النسخ الاحتياطي؛
  إعادة التشغيل لا تكرر ولا تفقد).
- الشاشات عديمة الحالة: callback_data يحمل الوجهة كاملة
  (`v1|screen|arg|page`)، ≤ 64 بايت؛ زر غير مفهوم/منتهٍ → تنبيه منبثق.

## 3 — الأمان

- allowlist بمعرّف محادثة المشغّل فقط؛ الغريب يُتجاهل ويُسجل.
- الأفعال المؤثرة: بطاقة تأكيد بزر يحمل nonce أحادي الاستخدام صلاحيته
  5 دقائق (in-memory — مشغّل واحد وعملية واحدة).
- كل النصوص الصادرة عبر `sanitize_secret_text`.

## 4 — الشاشات

- `/start` → القائمة: 📊 اليوم · 👥 العملاء · 🩺 الصحة · 💰 الأعمال ·
  🧾 الأخطاء · ⚙️ إجراءات.
- **اليوم**: حالة التشغيلة + counts + tenant_day_states لكل TEN + تفاصيل
  قرارات البوابة عند الطلب.
- **العملاء**: قائمة مرقمة (8/صفحة) → بطاقة: خطة، حالة رحلة، نافذة،
  آخر تسليمة، عدادات النتائج والحجب، عمر الاشتراك.
- **الصحة**: worker/timer (systemd)، توكن ميتا، عدّاد انتهاء توكن سلة،
  رصيد SearchAPI، حالة القوالب، عمر آخر نسخة احتياطية + فحوص حية
  عند الطلب.
- **الأعمال**: اشتراكات، مشتريات التحليل، تحويلات القمع، نسبة «قدمت»،
  تكلفة/عميل من §14 — نطاقات أسبوع/شهر/الكل.
- **الأخطاء**: آخر أسطر الخطأ من journald بعد الفلترة (أصناف استثناءات
  فقط، لا محتوى رسائل).
- **إجراءات** (موافقة مزدوجة): إعادة إرسال معلق، تشغيلة يدوية scoped
  (وحدة systemd عابرة + الملخص يصل آليًا)، إيقاف/استئناف عميل، إرسال
  قالب الصباح يدويًا (بعد الاعتماد).
- المهام الطويلة: «⏳ انطلق…» ثم تحرير الرسالة بالنتيجة.

## 5 — الاختبارات (قبل الكود، كالعادة)

- موجّه كامل بنقل زائف: تحديث خام ← ردود حرفية.
- هجومي: chat_id غريب يُتجاهل ويُسجل.
- عارضون ذهبيون؛ اختبار خلو PII يمسح كل العارضين.
- nonce: انتهاء، عدم إعادة، عدم تنفيذ مزدوج.
- صفحات على الحدود (0، 1، 8، 9 عناصر).

## 6 — خطة المراحل

| # | المحتوى | الخطر |
|---|---|---|
| 1 | النواة + الهوية + المؤشر + القائمة + «اليوم» و«الصحة» | صفر (قراءة) |
| 2 | «العملاء» + «الأعمال» | صفر |
| 3 | «الأخطاء» + الفحوص الحية | صفر |
| 4 | «إجراءات» بالموافقة المزدوجة | محدود — عبر السلطات فقط |
| 5 | تقرير أسبوعي تلقائي + صقل من الاستخدام | صفر |

كل مرحلة: سطر في CHANGELOG قبل الكود، اختبارات خضراء قبل الخدمة،
وصفر لمس لمسار العملاء.
