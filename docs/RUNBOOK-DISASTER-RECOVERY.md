# دليل التعافي من الكارثة

من «الخادم اختفى» إلى «الخدمة تعمل من جديد».

هذا الدليل مكتوب ليُتبع في الثالثة فجرًا وأنت متوتر.
اتبع الخطوات بالترتيب ولا تقفز.
كل خطوة تقول لك ما هو مؤتمت وما يجب أن تفعله بيدك.

آخر تحديث: الحادي والثلاثون من يوليو ٢٠٢٦.

---

## القاعدة الصفرية — اقرأها قبل أي شيء

النسخة الاحتياطية تحفظ **البيانات**، ولا تعيد بناء **الخادم** وحدها.

المحفوظ تلقائيًا كل ليلة في المستودع المشفّر:

- نسخة كاملة من قاعدة البيانات.
- ملفات العملاء كلها (السير الذاتية والمرفوعات والتقارير).
- إعداد بوابة الدخول وملفات وحدات النظام وبطاقة وصف الخادم.

المحفوظ في مستودع الكود على الإنترنت:

- الكود كله، وملفات الحاويات، وملفات الترحيل، وقفل الاعتماديات.

**غير المحفوظ عمدًا: ملف الأسرار.**

ملف الأسرار لا يُنسخ ولا يُرفع ولا يُخزن في أي مكان يخص المشروع.
هذا قرار معماري لا خلل — لكنه يعني أن إعادة البناء **موقوفة عليك أنت**.
إن لم تكن تملك القيم، لا يمكن لهذا الدليل ولا لأي أداة أن تُنهي التعافي.
القائمة الكاملة لأسماء المفاتيح ومصادرها في الملحق الأول أسفل هذا الملف.

**الخطر الأكبر — ثلاثة أسرار بدونها النسخة الاحتياطية نفسها بلا قيمة:**

```
RESTIC_PASSWORD
B2_ACCOUNT_ID
B2_ACCOUNT_KEY
```

كلمة مرور المستودع لا تُستخرج من أي مكان ولا يمكن استعادتها.
إن ضاعت فكل النسخ المحفوظة تصبح كتلة مشفّرة لا تُفتح أبدًا.
مكانها الصحيح: مدير كلمات المرور الخاص بك، خارج هذا الخادم تمامًا.

---

## قبل أن تبدأ — قائمة ما يجب أن يكون في يدك

- كلمة مرور المستودع المشفّر ومفتاحا التخزين السحابي.
- ملف الأسرار أو القيم التي تركّبه (الملحق الأول).
- صلاحية دخول إلى مستودع الكود على الإنترنت.
- صلاحية تعديل سجلات النطاق عند مسجّل النطاق.
- بطاقة دفع أو حساب جاهز لتشغيل خادم جديد.

الوقت المتوقع للتعافي الكامل: بين ساعة ونصف وثلاث ساعات.
أطول خطوة هي بناء صورة الحاوية، والأبطأ في العادة هو انتشار سجل النطاق.

---

## الخطوة الأولى — خادم جديد

جهّز خادمًا جديدًا بالمواصفات نفسها:

- نظام أوبونتو الإصدار الرابع والعشرين، معمارية عادية.
- ذاكرة أربعة غيغابايت على الأقل، وقرص أربعين غيغابايت على الأقل.
- دخول بصلاحية الجذر.
- المنفذان الثمانون والأربعمئة والثلاثة والأربعون مفتوحان للعالم.

**غير مؤتمت:** إنشاء الخادم يدوي بالكامل عند مزود الاستضافة.

سجّل عنوان الخادم الجديد، ستحتاجه في خطوة النطاق.

## الخطوة الثانية — تثبيت البرمجيات الأساسية

```bash
apt-get update
apt-get install -y docker.io docker-compose-v2 git curl restic \
    python3.12 python3.12-venv \
    libglib2.0-0t64 libpango-1.0-0 libpangoft2-1.0-0 libharfbuzz0b \
    libharfbuzz-subset0 libcairo2 libgdk-pixbuf-2.0-0 libffi8 \
    shared-mime-info \
    fonts-liberation fonts-dejavu-core fonts-noto-core
systemctl enable --now docker
```

مكتبات الخطوط والرسم في الأمر أعلاه ليست زائدة.
عامل التسليم يبني ملفات السير الذاتية على الخادم نفسه لا داخل الحاوية.
بدونها يعمل كل شيء ظاهريًا ثم يفشل التسليم في آخر خطوة فقط.

**حزم الخطوط الثلاث ليست ترفًا، وحذف أي واحدة منها لا يُنتج خطأ ولا رسالة.**
قالب السيرة يطلب خط ليبريشن أولًا، وتقرير التحليل العربي يطلب خط نسخ.
حين ينقص أحدهما لا يتوقف شيء: نظام الخطوط يستبدله بديلًا صامتًا،
فيخرج المستند بوجه خطّي لم تُعتمد عليه أي عيّنة، ويصل العميل هكذا.
لهذا يفحص سكربت التحقق النهائي الخطوط بالاسم في الخطوة الرابعة عشرة،
ويفحصها أيضًا اختبار في المستودع يرسم المستندين ويقرأ الوجه المضمّن فيهما.

ثم ثبّت بوابة الدخول من مستودعها الرسمي:

```bash
apt-get install -y debian-keyring debian-archive-keyring apt-transport-https
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/gpg.key' \
    | gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt' \
    | tee /etc/apt/sources.list.d/caddy-stable.list
apt-get update
apt-get install -y caddy
```

## الخطوة الثالثة — فتح المستودع المشفّر

أنشئ ملف إعداد النسخ الاحتياطي خارج مجلد الكود:

```bash
mkdir -p /root/.config/career-backup
chmod 700 /root/.config/career-backup
```

أنشئ الملف التالي واملأه بأربع قيم من مدير كلمات المرور:

```
/root/.config/career-backup/backup.env
```

المفاتيح المطلوبة فيه:

```
RESTIC_REPOSITORY
B2_ACCOUNT_ID
B2_ACCOUNT_KEY
RESTIC_PASSWORD
```

ثم أغلق صلاحياته:

```bash
chmod 600 /root/.config/career-backup/backup.env
```

تأكد أن المستودع يُقرأ قبل أن تكمل:

```bash
set -a; . /root/.config/career-backup/backup.env; set +a
export HOME=/root
restic snapshots --compact | tail -20
```

إن ظهرت لك قائمة اللقطات فأنت بأمان، وكل ما بعدها مجرد تنفيذ.
إن فشل هذا الأمر فتوقف هنا — لا فائدة من إكمال بقية الخطوات.

**ملاحظة:** أبقِ هذه الجلسة الطرفية مفتوحة.
بقية أوامر الاسترجاع تحتاج المتغيرات نفسها.

## الخطوة الرابعة — إحضار الكود

```bash
git clone https://github.com/2fahad2/career-platform.git /root/career
cd /root/career
git checkout main
```

النسخة التي كانت تعمل فعلًا مسجّلة داخل بطاقة وصف الخادم في النسخة الاحتياطية.
استخرجها الآن، ستحتاجها في أكثر من خطوة:

```bash
restic dump --tag config latest career-config.tar.gz > /tmp/career-config.tar.gz
mkdir -p /tmp/career-config
tar -xzf /tmp/career-config.tar.gz -C /tmp/career-config
cat /tmp/career-config/config/MANIFEST.txt
```

البطاقة تعطيك رقم النسخة التي كانت تعمل، ورقم آخر ترحيل مطبّق على القاعدة،
وقائمة أسماء مفاتيح الأسرار، وإصدارات كل البرمجيات، وأسماء المجلدات والحاويات.
لا تحوي أي قيمة سرية — أسماء وأرقام فقط.

## الخطوة الخامسة — البيئة الافتراضية

الخدمات الثلاث التي تعمل خارج الحاويات تحتاج بيئة بايثون على الخادم:

```bash
python3.12 -m venv /root/career/.venv
/root/career/.venv/bin/pip install --upgrade pip
/root/career/.venv/bin/pip install -r /root/career/requirements.lock
/root/career/.venv/bin/pip install -e /root/career --no-deps
```

التثبيت من ملف القفل لا من ملف المشروع — حتى تعود النسخ نفسها بالضبط.

## الخطوة السادسة — إعادة الأسرار

ابدأ من القالب المتتبَّع في مستودع الكود:

```bash
cp /root/career/.env.staging.example /root/career/.env.staging
chmod 600 /root/career/.env.staging
```

ثم املأ القيم واحدة واحدة من الملحق الأول.

**غير مؤتمت بالكامل، وهو أطول جزء بشري في الدليل.**
لا توجد أي أداة تستطيع ملء هذا الملف نيابة عنك.

للتأكد أن الملف مكتمل قبل أن تكمل — هذا الأمر يعدّ الأسماء ولا يطبع أي قيمة:

```bash
grep -cE '^[A-Za-z_][A-Za-z0-9_]*=' /root/career/.env.staging
```

يجب أن يكون العدد سبعة وثلاثين أو أكثر.
قارن الأسماء الناقصة ببطاقة وصف الخادم من الخطوة الرابعة.

## الخطوة السابعة — رفع الحاويات

```bash
cd /root/career
docker compose -f docker-compose.staging.yml --env-file .env.staging up -d --build
docker compose -f docker-compose.staging.yml --env-file .env.staging ps
```

بناء الصورة يستغرق عدة دقائق في أول مرة — هذا طبيعي.
تنتظر حتى تظهر الحاويات الثلاث بحالة سليمة.

قاعدة البيانات تُنشأ فارغة، ويُنشأ فيها حساب التطبيق تلقائيًا من الملف التالي:

```
/root/career/docker/initdb/10-app-role.sh
```

## الخطوة الثامنة — استرجاع قاعدة البيانات

```bash
restic dump --tag db latest career_staging.dump > /tmp/career_staging.dump
docker exec -i career_staging-postgres-1 \
    pg_restore -U career_owner -d career_staging --no-owner \
    < /tmp/career_staging.dump
```

ثم امسح الملف المؤقت فورًا — فيه بيانات عملاء حقيقية:

```bash
shred -u /tmp/career_staging.dump
```

تحقق سريعًا من عدد الجداول وعدد الجداول المحمية بعزل المستأجرين:

```bash
docker exec career_staging-postgres-1 psql -U career_owner -d career_staging -tAc \
    "SELECT count(*) FROM information_schema.tables WHERE table_schema='public'"
docker exec career_staging-postgres-1 psql -U career_owner -d career_staging -tAc \
    "SELECT count(*) FROM pg_class WHERE relrowsecurity = true"
```

العدد المتوقع اليوم: ستة وثلاثون جدولًا، وثلاثون منها بعزل مفعّل.
أي رقم أقل بكثير يعني أن الاسترجاع ناقص — أعده ولا تُكمل.

## الخطوة التاسعة — رفع المخطط إلى آخر ترحيل

النسخة المسترجَعة تعود إلى الليلة الماضية، وقد يكون الكود أحدث منها:

```bash
cd /root/career
docker compose -f docker-compose.staging.yml --env-file .env.staging \
    exec api alembic upgrade head
```

**انتبه:** ملفات الترحيل مخبوزة داخل صورة الحاوية.
إن كان الكود يحمل ترحيلًا أحدث من الصورة، أعد البناء أولًا:

```bash
docker compose -f docker-compose.staging.yml --env-file .env.staging up -d --build api
```

## الخطوة العاشرة — استرجاع ملفات العملاء

استرجع إلى مجلد مؤقت أولًا، ثم انسخ — لا تكتب فوق الجذر مباشرة:

```bash
restic restore --tag storage latest --target /tmp/restore-storage
mkdir -p /root/career/data
cp -a /tmp/restore-storage/root/career/data/. /root/career/data/
find /root/career/data -type f | wc -l
```

عدد الملفات يجب أن يطابق ما في اللقطة تقريبًا.
مجلد فارغ هنا يعني أن سير العملاء لم تُسترجع — لا تكمل قبل حلها.

## الخطوة الحادية عشرة — استرجاع إعداد البوابة ووحدات النظام

من الحزمة التي فككتها في الخطوة الرابعة:

```bash
cp /tmp/career-config/config/caddy/Caddyfile /etc/caddy/Caddyfile
systemctl reload caddy
cp /tmp/career-config/config/systemd/career-* /etc/systemd/system/
systemctl daemon-reload
```

هذه هي الفجوة التي كانت مفتوحة قبل الحادي والثلاثين من يوليو.
إعداد البوابة كان يعيش على الخادم فقط، ولم يكن له أي نسخة في أي مكان آخر.

نسخة احتياطية ثانية من ملفات الوحدات موجودة داخل الكود أيضًا:

```
/root/career/ops/systemd/
```

استعمل نسخة الحزمة أولًا — فهي التي كانت تعمل فعلًا لحظة الكارثة.

## الخطوة الثانية عشرة — النطاق والشهادة

**غير مؤتمت إطلاقًا، ويجب أن يتم يدويًا عند مسجّل النطاق.**

خوادم الأسماء للنطاق هي خوادم مسجّل النطاق نفسه.
عدّل السجل من نوع أ ليشير إلى عنوان الخادم الجديد:

```
api.career-platform.net
```

انتظر حتى ينتشر التغيير، ثم تأكد أن العنوان صار الجديد:

```bash
dig +short api.career-platform.net
```

بعدها تصدر الشهادة تلقائيًا في أول طلب، ثم تحقق:

```bash
curl -s https://api.career-platform.net/health
```

الرد المتوقع يبدأ بحالة سليمة ويذكر أن القاعدة والذاكرة المؤقتة تعملان.

الانتشار قد يأخذ من دقائق إلى ساعات حسب المسجّل.
لا شيء يمكنك فعله لتسريعه — انتقل للخطوات التالية وعد إليه لاحقًا.

## الخطوة الثالثة عشرة — تشغيل الخدمات

```bash
systemctl enable --now career-worker.service career-admin-bot.service
systemctl enable --now career-backup.timer career-engine-nightly.timer career-restore-test.timer
systemctl list-timers 'career*' --all
```

الوحدتان الأوليان دائمتان: عامل المحادثات وبوت الإشراف.
المؤقتات الثلاثة مجدولة بتوقيت الرياض: النسخ الاحتياطي ثم التشغيل الليلي ثم اختبار الاسترجاع الشهري.

وحدة التنبيه لا تُفعَّل ولا تُشغَّل — تستدعيها بقية الوحدات عند فشلها النهائي.
وجود ملفها في مجلد النظام يكفي.

## الخطوة الرابعة عشرة — التحقق النهائي

```bash
/root/career/scripts/verify_restore.sh
```

هذا السكربت يقرأ ولا يكتب شيئًا أبدًا، ويفحص تسعة أمور:

- وجود ملف الأسرار وعدد مفاتيحه، وأن صلاحياته مغلقة على المالك وحده.
- الحاويات الثلاث وحالتها الصحية.
- تطابق آخر ترحيل في القاعدة مع أحدث ترحيل في الكود.
- عدد الجداول وعزل المستأجرين وإجباره.
- وجود ملفات العملاء فعليًا.
- الوحدات مثبتة ومفعّلة وحية، وجدولة المؤقتات قادمة، وآخر تشغيل نجح.
- البوابة تعمل والفحص الصحي يرد محليًا ومن الإنترنت.
- سلسلة النسخ الاحتياطي حية وآخر لقطة حديثة.
- خطوط المستندات موجودة بأسمائها، فلا يُرسم مستند بوجه بديل صامت.

خروج بصفر يعني أن التعافي اكتمل فعلًا.
أي فشل معروض بالتفصيل مع الأمر الذي يفتح سجله.

**لا تعلن انتهاء التعافي قبل أن يخرج هذا السكربت بصفر.**

## الخطوة الخامسة عشرة — ما بعد التعافي

راجع هذه الأمور في اليوم نفسه:

- إن تغيّر النطاق أو المسار، حدّث عنوان الاستقبال في لوحة سلة وفي لوحة ميتا.
- إن أنشأت مفاتيح جديدة، ألغِ القديمة من لوحات المزودين حتى لا تبقى صالحة.
- شغّل نسخة احتياطية يدوية أولى على الخادم الجديد وتأكد من نجاحها:

```bash
/root/career/ops/backup/backup.sh
```

- شغّل اختبار استرجاع كامل للتأكد أن السلسلة الجديدة قابلة للاسترجاع:

```bash
/root/career/ops/backup/restore-test.sh
```

- أخبر العملاء النشطين إن كان الانقطاع تجاوز يوم تسليم كاملًا.

## الملحق الأول — الأسرار: الأسماء ومصادرها

القاعدة المطلقة في هذا الملف: **أسماء فقط، ولا قيمة واحدة مكتوبة هنا ولا في أي مخرج.**

### مجموعة أولى: أسرار تختارها أنت بنفسك

```
DB_PASSWORD
DB_OWNER_PASSWORD
REDIS_PASSWORD
WHATSAPP_VERIFY_TOKEN
RESTIC_PASSWORD
```

الثلاثة الأولى تُولَّد جديدة بحرية عند إعادة البناء.
حسابات قاعدة البيانات تُنشأ من جديد بكلمات المرور التي تضعها في ملف الأسرار،
والنسخة المسترجَعة لا تحمل كلمات مرور بداخلها.

الرابع يجب أن يطابق حرفيًا ما هو مسجّل في لوحة ميتا، وإلا رُفض ربط الاستقبال.

الخامس استثناء خطير: لا يُختار من جديد بعد الكارثة.
لو غيّرته لن تفتح النسخ القديمة أبدًا — يجب أن يكون هو نفسه القديم.

### مجموعة ثانية: التخزين السحابي للنسخ الاحتياطية

```
RESTIC_REPOSITORY
B2_ACCOUNT_ID
B2_ACCOUNT_KEY
```

المصدر: لوحة تحكم باكبليز، قسم مفاتيح التطبيقات.
المفتاح يُنشأ من جديد بسهولة، لكن مسار المستودع يجب أن يطابق القديم بالضبط.

### مجموعة ثالثة: أنثروبيك

```
ANTHROPIC_API_KEY
```

المصدر: لوحة تحكم أنثروبيك، قسم المفاتيح.
المفتاح القديم لا يُقرأ بعد إنشائه — أنشئ مفتاحًا جديدًا وألغِ القديم.

### مجموعة رابعة: سلة

```
SALLA_WEBHOOK_SECRET
SALLA_API_KEY
SALLA_CLIENT_ID
SALLA_CLIENT_SECRET
SALLA_REFRESH_TOKEN
SALLA_TOKEN_EXPIRES_AT
SALLA_PRODUCT_CATALOG
SALLA_PRODUCT_PRICING
```

المصدر: لوحة شركاء سلة، صفحة التطبيق الخاص بك.
معرّف التطبيق وسره يظهران في إعدادات التطبيق.
سر الاستقبال يظهر في صفحة إعداد الأحداث ويمكن توليده من جديد هناك.
آخر مفتاحين ليسا سرًا: خريطة المنتجات وأسعارها، وتُعاد كتابتهما من صفحة منتجات المتجر.
مفتاح التحديث ووقت انتهائه محفوظان لتجديد الوصول يدويًا، والكود اليوم لا يقرؤهما.

### مجموعة خامسة: ميتا وواتساب

## الملحق الثاني — ما ليس مؤتمتًا، بصراحة

هذه الأشياء لا يفعلها أي سكربت، ويجب أن تفعلها بيدك:

- إنشاء الخادم عند مزود الاستضافة وفتح المنفذين.
- ملء ملف الأسرار كاملًا — أطول جزء بشري في الدليل.
- ملء ملف إعداد النسخ الاحتياطي بمفاتيح التخزين وكلمة مرور المستودع.
- تعديل سجل النطاق عند المسجّل، وانتظار انتشاره.
- تحديث عنوان الاستقبال في لوحتي سلة وميتا إن تغيّر النطاق.
- إلغاء المفاتيح القديمة بعد إصدار البديل.
- قرار إبلاغ العملاء بالانقطاع.

وهذه أشياء محفوظة لكنها ليست مضمونة بلا انتباه:

- شهادة التشفير لا تُنسخ احتياطيًا، وتُصدر من جديد تلقائيًا بعد ضبط النطاق.
- محتوى الذاكرة المؤقتة لا يُنسخ — الطوابير غير المنجزة تضيع، وهذا مقبول بالتصميم.
- ملفات الوحدات في الحزمة قد تكون أقدم من نسختها في الكود إن عُدّلت ولم تُثبَّت.

## الملحق الثالث — أوامر تشخيص سريعة

سجل خدمة معيّنة:

```bash
journalctl -u career-worker.service -n 100 --no-pager
```

حالة كل الوحدات دفعة واحدة:

```bash
systemctl list-unit-files 'career*'
```

آخر اللقطات في المستودع المشفّر:

```bash
restic snapshots --compact | tail -20
```

قفل عالق يمنع تنظيف اللقطات القديمة:

```bash
restic unlock
```

سجلات الحاويات:

```bash
docker compose -f docker-compose.staging.yml --env-file .env.staging logs --tail 100
```
